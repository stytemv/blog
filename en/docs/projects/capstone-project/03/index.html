캡스톤 프로젝트 #3 — mmap() 호출 인자 추적​

1. 목표와 출발점​

이번 단계에서는 eBPF로 Linux 프로세스의 mmap() 시스템 콜 진입을 관찰하고, 프로세스가 어떤 조건으로 가상 메모리 매핑을 요청했는지 기록한다.

이전 단계까지 구현한 memwatch는 다음 기능을 갖추고 있다.

  • libbpf Skeleton을 통해 eBPF 프로그램을 open/load/attach/destroy
  • 지정한 PID만 추적하는 BPF ARRAY Map 기반 필터링
  • sudo ./memwatch <PID> 형태의 기존 프로세스 감시
  • sudo ./memwatch ./victim.out 형태의 대상 프로그램 실행 및 감시
  • eBPF Ring Buffer로 이벤트를 User-space에 전달하고 callback에서 출력
  • 이벤트의 timestamp, PID(TGID), TID, COMM 수집

기존 출력은 대체로 [MMAP] TIME=... PID=... TID=... COMM=... 형태였다.

여기서 mmap의 인자 여섯 개를 추가한다.

이번 단계에서는 sys_enter_mmap을 통해 addr, length, prot, flags, fd, offset 정보를 수집한다.​

2. mmap()은 무엇을 요청하는가?​

void *mmap(void *addr, size_t length,
           int prot, int flags,
           int fd, off_t offset);

mmap()은 프로세스의 가상 주소 공간에 매핑을 생성하도록 요청하는 인터페이스다.

다만 메모리 매핑이 곧 물리 메모리 페이지의 할당을 의미하는 것은 아니다.

테스트 프로그램인 victim.c에서는 다음과 같이 mmap()을 호출한다.

void *addr = mmap(
    NULL,
    page_size,
    PROT_READ | PROT_WRITE,
    MAP_PRIVATE | MAP_ANONYMOUS,
    -1,
    0
);

각 인자의 의미는 다음과 같다.

인자전달 값의미
addr (첫 번째 인자)NULL매핑할 가상 주소를 커널이 선택하도록 함
lengthpage_size시스템의 페이지 크기만큼 매핑 요청
protPROT_READ | PROT_WRITE읽기 및 쓰기 권한 요청
flagsMAP_PRIVATE | MAP_ANONYMOUSPrivate Anonymous Mapping 요청
fd-1Anonymous Mapping이므로 파일 디스크립터를 사용하지 않음
offset0Anonymous Mapping이므로 파일 오프셋을 사용하지 않음

prot와 flags의 차이​

prot는 그 매핑에 어떤 메모리 접근을 허용할지 지정한다.

상수일반적인 값(x86-64 Linux)의미
PROT_READ0x1읽기
PROT_WRITE0x2쓰기
PROT_EXEC0x4실행

반면 flags는 매핑을 어떻게 생성하고 공유할지 지정한다.

상수일반적인 값(x86-64 Linux)의미
MAP_PRIVATE0x2수정 사항을 다른 매핑과 공유하지 않는 private mapping
MAP_ANONYMOUS0x20파일이 아닌 anonymous mapping
MAP_FIXED0x10요청 주소에 고정 매핑하려는 옵션. 기존 매핑 교체 위험이 있음

위 상수들은 비트 플래그이므로 | 연산으로 결합한다.

PROT_READ | PROT_WRITE
= 0x1 | 0x2
= 0x3

MAP_PRIVATE | MAP_ANONYMOUS
= 0x2 | 0x20
= 0x22

따라서 이번 테스트에서 prot=0x3, flags=0x22가 나오면 프로그램의 요청과 부합한다.

3. ctx는 누가 만들고, 누가 채우는가?​

기존 eBPF 함수는 다음과 같은 형태다.

SEC("tracepoint/syscalls/sys_enter_mmap")
int trace_mmap(struct trace_event_raw_sys_enter *ctx)
{
    /* ... */
}

여기서 ctx는 trace_mmap()의 매개변수로, 커널의 syscall tracing 및 BPF 실행 경로다.

  1. 사용자 프로그램이 mmap() 시스템 콜에 진입한다.
  2. 커널의 syscall 진입 추적 경로에서 현재 시스템 콜의 인자들을 확보한다.
  3. 해당 tracepoint에 연결된 eBPF 프로그램이 읽을 수 있는 형태로 이벤트 context를 준비한다.
  4. 커널의 BPF 실행 경로가 이 context를 전달해 프로그램을 실행한다.
  5. 우리 코드는 이미 준비된 ctx->args[]를 읽는다.
victim: mmap(addr, len, prot, flags, fd, offset)
                      |
                      v
              Linux syscall 진입
                      |
                      v
           Kernel syscall tracing
          (인자 추출 및 context 준비)
                      |
                      v
      tracepoint/syscalls/sys_enter_mmap
                      |
                      v
              trace_mmap(ctx)
                      |
                      +-- ctx->args[0] : addr
                      +-- ctx->args[1] : length
                      +-- ctx->args[2] : prot
                      +-- ctx->args[3] : flags
                      +-- ctx->args[4] : fd
                      +-- ctx->args[5] : offset

eBPF 코드의 ctx가 먼저 전달되고 나중에 tracepoint가 값을 채우는 구조가 아니다.

커널이 필요한 이벤트 데이터를 준비한 다음, eBPF 코드가 이를 읽는 구조다.

ctx와 뒤에서 등장할 e는 역할이 다르다.

  • ctx: 커널이 준비한 입력 context. 시스템 콜 인자를 읽는다.
  • e: 우리가 Ring Buffer에 예약한 출력 이벤트. 필요한 정보를 복사해 User-space에 보낸다.

즉, 데이터 경로는 ctx → e → Ring Buffer → memwatch.c다.

4. 코드 변경 구조​

이전 구현의 Skeleton, PID 필터, Ring Buffer는 유지하고 세 파일만 변경한다.

파일변경 내용

memwatch.bpf.cctx->args[]를 읽어 Ring Buffer 이벤트에 저장

4.1. memwatch.h: 공통 이벤트 구조체 확장​

기존 mem_event의 필드를 보존하고 mmap 인자 저장 공간을 추가한다.

#ifndef MEMWATCH_H
#define MEMWATCH_H

/*
 * Event Type
 * 발생한 메모리 관련 이벤트의 종류를 구분
 * 추후 mprotect, munmap 등 추가 예정
 */
enum mem_event_type {
    MEM_EVENT_MMAP = 1,
};

/*
 * Memory Event
 * eBPF에서 생성하여 Ring Buffer를 통해
 * User-space로 전달할 공통 데이터 구조체
 *
 * __u32, __u64는 이 헤더를 포함하기 전에 정의되어 있어야 함
 */
struct mem_event {
    __u64 timestamp_ns;     // 이벤트 발생 시각 (커널 단조 시계 기준, ns)

    __u32 pid;              // 프로세스 ID (TGID)
    __u32 tid;              // 스레드 ID (TID)
    __u32 type;             // 이벤트 종류 (mem_event_type)
    __u32 reserved;         // 구조체 정렬을 위한 예약 영역

    char comm[16];          // 프로세스 실행 이름 (TASK_COMM_LEN)

    /*
     * mmap() Arguments
     * sys_enter_mmap에서 수집한 인자. 실제 반환 주소가 아니라 요청 값이다.
     * 성공 여부/반환 주소는 다음 단계의 sys_exit_mmap에서 다룬다.
     */
    __u64 addr;             // 요청 가상 주소
    __u64 length;           // 요청 크기 (bytes)
    __u64 prot;             // 요청 접근 권한
    __u64 flags;            // 매핑 옵션
    __s64 fd;               // 파일 디스크립터 (음수 표현 필요)
    __u64 offset;           // 파일 오프셋
};

#endif

__u64는 64비트 unsigned 정수, __s64는 64비트 signed 정수다. fd는 -1처럼 음수가 유효하므로 signed 형식으로 저장한다.

4.2. memwatch.bpf.c: Tracepoint 인자 추출​

기존의 PID 필터링, Ring Buffer 예약, 이벤트 데이터 작성 코드를 유지하고 ctx->args[] 복사를 추가했다.

#include "vmlinux.h"
#include "memwatch.h"

#include <bpf/bpf_helpers.h>

char LICENSE[] SEC("license") = "GPL";

/*
 * Ring Buffer Map
 * eBPF에서 생성한 이벤트를 User-space로 전달
 */
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);
} events SEC(".maps");

/*
 * Target PID Map
 * User-space에서 전달한 감시 대상 PID를 저장
 *
 * ARRAY Map:
 *   key   = 0
 *   value = 감시할 PID
 */
struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, __u32);
} target_pid_map SEC(".maps");

SEC("tracepoint/syscalls/sys_enter_mmap")
int trace_mmap(struct trace_event_raw_sys_enter *ctx)
{
    __u64 id = bpf_get_current_pid_tgid();  // 상위 32bit: TGID(PID), 하위 32bit: TID
    __u32 pid = id >> 32;
    __u32 tid = (__u32)id;

    /*
     * PID Filtering
     * BPF Map에서 감시 대상 PID를 읽고 현재 PID와 비교
     */
    __u32 key = 0;
    __u32 *target_pid = bpf_map_lookup_elem(&target_pid_map, &key);

    if (!target_pid || *target_pid == 0 || pid != *target_pid)
        return 0;

    /*
     * Ring Buffer Reserve
     * 이벤트 구조체 하나를 저장할 공간 확보
     */
    struct mem_event *e = bpf_ringbuf_reserve(
        &events,
        sizeof(struct mem_event),
        0
    );

    if (!e)
        return 0;

    /* Event 데이터 작성 */
    e->timestamp_ns = bpf_ktime_get_ns();
    e->pid = pid;
    e->tid = tid;
    e->type = MEM_EVENT_MMAP;
    e->reserved = 0;

    bpf_get_current_comm(e->comm, sizeof(e->comm));  // 현재 실행 이름을 가져옴

    /*
     * mmap() Arguments 추출
     * sys_enter에서는 요청 인자만 읽을 수 있고 반환값은 알 수 없다.
     *
     * mmap(addr, length, prot, flags, fd, offset)
     *  args[0] = addr
     *  args[1] = length
     *  args[2] = prot
     *  args[3] = flags
     *  args[4] = fd
     *  args[5] = offset
     */
    e->addr   = ctx->args[0];
    e->length = ctx->args[1];
    e->prot   = ctx->args[2];
    e->flags  = ctx->args[3];

    /*
     * fd의 원래 타입은 int(32-bit)다.
     * 0xFFFFFFFF가 64-bit 양수 4294967295로 보이지 않도록
     * 먼저 signed 32-bit로 해석한 뒤 저장한다.
     */
    e->fd     = (__s32)ctx->args[4];
    e->offset = ctx->args[5];

    /* 작성한 이벤트를 Ring Buffer에 제출 */
    bpf_ringbuf_submit(e, 0);

    return 0;
}

순서​

  1. bpf_get_current_pid_tgid()로 현재 프로세스와 스레드 정보를 가져온다.
  2. target_pid_map의 key 0에서 감시 PID를 읽는다.
  3. 감시 대상이 아니면 즉시 return 0 한다.
  4. 대상이면 Ring Buffer에 struct mem_event 한 건의 공간을 예약한다.
  5. PID/TID/COMM, timestamp와 mmap 인자를 채운다.
  6. bpf_ringbuf_submit()으로 이벤트를 게시한다.

ctx->args[2]를 e->prot에 저장하는 한 줄을 예로 들면 다음과 같다.

e->prot = ctx->args[2];

이는 커널이 기록한*세 번째 syscall 인자를 우리가 정의한 이벤트 구조체에 복사하는 동작이다.

4.3. memwatch.c: Ring Buffer Callback 출력​

/*
 * Ring Buffer Callback
 * Kernel에서 전달된 이벤트를 공통 구조체로 해석하여 출력
 */
static int handle_event(void *ctx, void *data, size_t data_sz)
{
    (void)ctx;

    const struct mem_event *e = data;

    if (data_sz < sizeof(*e))
        return 0;

    if (e->type == MEM_EVENT_MMAP) {
      /*
      * mmap() Event 출력
      *
      * Ring Buffer를 통해 수신한 mem_event 구조체에서
      * PID/TID/COMM과 mmap() 호출 인자를 출력한다.
      *
      * prot와 flags는 비트 플래그이므로 16진수로 출력한다.
      * addr 역시 가상 메모리 주소이므로 16진수로 출력한다.
      *
      * 현재는 syscall Entry Event이므로
      * 실제 매핑 주소 및 성공 여부는 출력하지 않는다.
      */
        printf("[MMAP] TIME=%llu PID=%u TID=%u COMM=%s\n",
               (unsigned long long)e->timestamp_ns,
               e->pid,
               e->tid,
               e->comm);

        printf("       addr=0x%llx length=%llu\n",
               (unsigned long long)e->addr,
               (unsigned long long)e->length);

        printf("       prot=0x%llx flags=0x%llx\n",
               (unsigned long long)e->prot,
               (unsigned long long)e->flags);

        printf("       fd=%lld offset=%llu\n",
               (long long)e->fd,
               (unsigned long long)e->offset);
    
    
    }

    return 0;
}

이 함수의 ctx는 앞서 설명한 eBPF의 trace_mmap(ctx)와 전혀 다른 매개변수**다. handle_event()의 ctx는 libbpf Ring Buffer Callback에 등록할 때 넘기는 사용자 정의 context 포인터이고, 현재 ring_buffer__new(..., handle_event, NULL, NULL)로 등록했으므로 NULL이다. data가 실제 Ring Buffer 이벤트를 가리킨다.

timestamp_ns는 bpf_ktime_get_ns()로 가져온 단조 시계(monotonic clock) 기준 나노초 값이다.

5. Makefile​

Makefile은 다음 빌드 흐름을 사용한다.

memwatch.bpf.c
      |
      v
memwatch.bpf.o  -- bpftool gen skeleton --> memwatch.skel.h
                                              |
memwatch.c + memwatch.h -----------------------+
      |
      v
memwatch.o
      |
      v
memwatch (libbpf, libelf, zlib 링크)

핵심 규칙은 다음과 같다.

CC := gcc
CLANG := clang
BPFTOOL := bpftool

TARGETS := memwatch victim.out

# Source files
USER_SRCS := memwatch.c
BPF_SRCS := memwatch.bpf.c

# Generated files
USER_OBJS := $(USER_SRCS:.c=.o)
BPF_OBJS := $(BPF_SRCS:.c=.o)
BPF_SKELS := $(BPF_SRCS:.bpf.c=.skel.h)
USER_DEPS := $(USER_OBJS:.o=.d)

# Compiler options
CFLAGS := -g -O2 -Wall -Wextra -MMD -MP
BPF_CFLAGS := -g -O2 -target bpf -D__TARGET_ARCH_x86 -I.
LDLIBS := -lbpf -lelf -lz

.PHONY: all clean rebuild

all: $(TARGETS)

# Compile eBPF programs
%.bpf.o: %.bpf.c memwatch.h vmlinux.h
	$(CLANG) $(BPF_CFLAGS) -c $< -o $@

# Generate skeleton headers
%.skel.h: %.bpf.o
	$(BPFTOOL) gen skeleton $< > $@

# Userspace objects depend on skeleton headers
$(USER_OBJS): $(BPF_SKELS)

# Compile userspace programs
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

# Link executable
memwatch: $(USER_OBJS)
	$(CC) $(USER_OBJS) -o $@ $(LDLIBS)

# Test victim
victim.out: victim.c
	$(CC) $(CFLAGS) $< -o $@

# Full rebuild
rebuild:
	$(MAKE) clean
	$(MAKE) all

# Remove generated files
clean:
	rm -f $(TARGETS) $(USER_OBJS) $(USER_DEPS) \
	      $(BPF_OBJS) $(BPF_SKELS)

-include $(USER_DEPS)

6. 실행 방법​

현재 구현에는 대상 프로그램을 실행하면서 추적하는 launcher 모드가 있다. 따라서 PID를 수동으로 확인할 필요 없이 다음과 같이 실행할 수 있다.

make
sudo ./memwatch ./victim.out

같은 프로그램은 기존 프로세스를 대상으로 다음처럼 실행할 수도 있다.

sudo ./memwatch <PID>

단, PID 모드에서는 감시 프로그램을 attach하기 전에 이미 발생한 이벤트를 볼 수 없다.

7. 실제 실험 결과​

7.1. victim.c가 직접 요청한 4096바이트 매핑​

실제로 관찰한 출력은 다음과 같다.


`addr=0x0`이 **잘못 수집된 주소라는 의미는 아니다.** 이번 시스템 콜에서 사용자가 요청한 첫 번째 인자가 `NULL`이라는 의미다. 실제 반환 주소는 아직 eBPF가 수집하지 않는다.

### 7.2. `main()` 전에 여러 `mmap` 이벤트가 발생한 이유

로그에서는 명시적으로 작성한 4096바이트 `mmap()`보다 먼저 여러 이벤트가 출력됐다.


동적으로 링크된 프로그램에서는 `main()` 실행 전에 dynamic linker와 라이브러리 초기화 과정에서 여러 매핑이 생성될 수 있다. 

따라서 PID가 모두 `victim.out`이라고 해서 **모든 `mmap()`을 우리가 `main()`에 직접 작성한 호출로 해석해서는 안 된다.

세 번째 예의 값은 다음처럼 읽을 수 있다.

```text
prot=0x5  = PROT_READ | PROT_EXEC
flags=0x812 = MAP_PRIVATE | MAP_FIXED | MAP_DENYWRITE
fd=3     = 당시 프로세스에서 열려 있던 파일 디스크립터 3

파일 디스크립터와 offset을 사용하는 file-backed 실행 가능 매핑 요청으로 해석할 수 있다. 동적 라이브러리 로딩과 관련된 것일 가능성이 높지만, 이 로그만으로 그 파일이 libc.so.6인지 등 정확한 대상 파일까지 확정할 수는 없다.

추후 /proc/<pid>/maps, file identity, ELF PT_LOAD 정보를 연계해야 한다.

또한 시스템 콜 Entry의 length가 반드시 페이지 크기의 배수로 출력되는 것은 아니다. 예를 들어 length=65827도 관측됐다. 이 값은 요청 길이이고, 실제 매핑 범위는 커널 처리 결과를 확인해야 한다.

8. 오류: fd=-1이 4294967295로 출력됨​

첫 번째 실행에서는 victim.c가 fd=-1을 전달했는데도 다음처럼 나왔다.

[MMAP] TIME=2806316727531 PID=17243 TID=17243 COMM=victim.out
       addr=0x0 length=4096
       prot=0x3 flags=0x22
       fd=4294967295 offset=0

원인​

이전 BPF 코드는 다음과 같았다.

e->fd = (__s64)ctx->args[4];

mmap()의 fd 인자는 C 수준에서 int(일반적인 x86-64 Linux에서 32비트 signed)이다. 그러나 syscall tracepoint의 args[]는 머신 워드 단위의 값을 제공하므로, 관찰된 환경에서는 -1의 하위 32비트 비트 패턴이 0xFFFFFFFF로 보였다.

32-bit -1  : 0xFFFFFFFF
unsigned  : 4294967295

여기서 곧바로 64비트 signed로 해석하면 이미 4294967295인 양수 값이 유지된다. 단순히 출력 형식만 %lld로 바꿔서는 해결되지 않는다.

수정​

/* 잘못 해석되던 방식 */
e->fd = (__s64)ctx->args[4];

/* 수정한 방식: 32-bit signed로 해석한 뒤 저장 */
e->fd = (__s32)ctx->args[4];

memwatch.h에서도 필드는 음수 표현이 가능한 signed 타입으로 유지한다.

__s64 fd;

그리고 User-space에서는 signed 출력 서식을 사용한다.

printf("fd=%lld\n", (long long)e->fd);

재실행 결과 다음처럼 정상적으로 출력됐다.

[MMAP] TIME=2986353656306 PID=17337 TID=17337 COMM=victim.out
       addr=0x0 length=4096
       prot=0x3 flags=0x22
       fd=-1 offset=0

즉, 문제가 victim.c에 있었던 것은 아니다.

syscall 인자 타입과 eBPF 이벤트 필드 사이의 부호 해석 문제였다.

9. 구현하면서 헷갈린 개념​

ctx는 어디서 왔는가?

trace_mmap(struct trace_event_raw_sys_enter *ctx)에서 ctx는 커널 BPF 실행 경로가 제공하는 입력 포인터다.

우리가 호출자 코드를 따로 작성하는 것이 아니다. Linux 커널의 syscall tracing 코드가 인자를 추출하고, BPF가 읽을 수 있는 context를 준비한다.

10. 다음 단계​

로그에 예를 들어 prot=0x5가 보인다고 그 매핑의 실행 권한이 최종적으로 설정됐다고 입증한 것은 아니다. 또한 현재는 각 매핑의 실제 주소, 성공 여부는 추적하지 않는다.

이러한 확정을 하기 위해 다음에는 sys_exit_mmap을 추적하고 mprotect의 인자와 반환값을 얻어온다.
