개요

아직 user-space loader나 Ring Buffer는 구현하지 않았다.

전체 구조는 다음과 같다.

victim 프로그램 실행
        ↓
mmap() syscall
        ↓
sys_enter_mmap tracepoint
        ↓
eBPF program 실행
        ↓
bpf_printk()
        ↓
trace_pipe에서 확인

BPF object의 load와 attach는 별도의 user-space 프로그램을 작성하지 않고 bpftool을 이용해 수동으로 수행했다.

1. Victim 프로그램 작성​

먼저 eBPF 프로그램이 관찰할 대상 프로그램을 작성했다.

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/mman.h>

int main(void)
{
    pid_t pid = getpid();

    long page_size = sysconf(_SC_PAGESIZE);
    if (page_size == -1) {
        perror("sysconf");
        return 1;
    }

    printf("PID: %d\n", pid);
    printf("Page size: %ld bytes\n\n", page_size);

    /*
     * Step 1
     * Anonymous memory mapping:
     *   permission = Read + Write
     */
    void *addr = mmap(
        NULL,
        page_size,
        PROT_READ | PROT_WRITE,
        MAP_PRIVATE | MAP_ANONYMOUS,
        -1,
        0
    );

    if (addr == MAP_FAILED) {
        perror("mmap");
        return 1;
    }

    printf("[1] mmap()\n");
    printf("    address : %p\n", addr);
    printf("    size    : %ld\n", page_size);
    printf("    perm    : RW-\n");
    printf("\nPress Enter to call mprotect()...\n");
    getchar();

    /*
     * Step 2
     * Change permission:
     *   Read + Write
     *       ->
     *   Read + Execute
     */
    if (mprotect(addr, page_size, PROT_READ | PROT_EXEC) == -1) {
        perror("mprotect");
        munmap(addr, page_size);
        return 1;
    }

    printf("\n[2] mprotect()\n");
    printf("    address : %p\n", addr);
    printf("    size    : %ld\n", page_size);
    printf("    perm    : RW- -> R-X\n");
    printf("\nPress Enter to call munmap()...\n");
    getchar();

    /*
     * Step 3
     * Remove the mapping.
     */
    if (munmap(addr, page_size) == -1) {
        perror("munmap");
        return 1;
    }

    printf("\n[3] munmap()\n");
    printf("    address : %p\n", addr);
    printf("    mapping removed\n");

    return 0;
}

malloc()은 C library의 user-space memory allocator이므로, 호출 시 항상 새로운 kernel memory mapping이 생성되는 것은 아니다. 따라서 kernel 수준에서 memory mapping의 생성과 permission 변화를 명확하게 관찰하기 위해 mmap()을 직접 사용했다. 이 프로그램은 하나의 anonymous memory region에 대해 다음 순서로 동작한다.

mmap()
   ↓
RW-
   ↓
mprotect()
   ↓
R-X
   ↓
munmap()

3. Kernel BTF와 'vmlinux.h'​

eBPF 프로그램에서는 kernel의 자료구조와 type definition이 필요하다.

현재 Linux kernel은 BTF 정보를 다음 경로에 제공하고 있다.

/sys/kernel/btf/vmlinux

여기서 /sys/kernel/btf/vmlinux 자체는 C header가 아니라 kernel의 BTF metadata이다. 그러므로 사용하기 위해 c header 형태로 변환이 필요하다.

bpftool을 사용하여 BTF 정보를 C header 형태로 변환할 수 있다.

bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h

결과적으로 프로젝트 디렉터리에:

vmlinux.h

를 생성하여 사용 할 수 있다.

#include "vmlinux.h"

4. 첫 eBPF 프로그램 작성​

memwatch.bpf.c를 다음과 같이 작성했다.

#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

char LICENSE[] SEC("license") = "GPL";

SEC("tracepoint/syscalls/sys_enter_mmap") //victim의 mmap() 호출 -> syscalls:sys_enter_mmap tracepoint 발생
int trace_mmap(struct trace_event_raw_sys_enter *ctx)
{
    __u64 id = bpf_get_current_pid_tgid(); // 현재 프로세스의 TGID와 TID를 64-bit 값으로 반환
                                           // 상위 32bit: TGID(PID), 하위 32bit: TID
    __u32 pid = id >> 32;
    __u32 tid = (__u32)id;

    char comm[16];
    bpf_get_current_comm(&comm, sizeof(comm)); // 현재 프로세스의 실행 이름(comm)을 가져옴

    bpf_printk("PID=%u TID=%u COMM=%s", pid, tid, comm);

    return 0;
}
mmap이 발생 -> 어떤 process/thread가 호출했는가?

현재 코드는 단순하게 이것만 확인한다.

5. PID와 TID​

다음 helper를 사용했다.

bpf_get_current_pid_tgid()

이 함수는 64-bit 값을 반환한다.

구조는 다음과 같다.

63                    32 31                     0
+-----------------------+------------------------+
|         TGID          |          PID           |
+-----------------------+------------------------+

Linux kernel 기준으로는:

상위 32 bit = TGID
하위 32 bit = PID

이다.

일반적인 user-space 관점에서는 TGID가 흔히 process ID로 사용되기 때문에 코드에서는 다음과 같이 이름을 붙였다.

여기서 pid는 victim에서:

getpid()

로 얻은 값과 비교할 수 있다.

단일 thread 프로그램이므로 현재 victim에서는:

PID == TID

가 된다.

6. COMM 얻기​

현재 task의 이름은 다음 helper로 얻었다.

bpf_get_current_comm(&comm, sizeof(comm));

현재 victim 실행파일 이름은:

victim.out

이므로 BPF 결과에서도

COMM=victim.out

이 출력되는 것을 확인 할 수 있다.

7. bpf_printk()​

현재는 Ring Buffer를 사용하지 않았다.

BPF program이 실제 실행되는지 확인하기 위해 다음을 사용했다.

bpf_printk(...)

흐름은 다음과 같다.

BPF program
    ↓
bpf_printk()
    ↓
Kernel tracing buffer
    ↓
cat /sys/kernel/debug/tracing/trace_pipe
    ↓
User space에서 확인

출력은 Linux tracing subsystem을 통해 확인할 수 있다.

trace_pipe는 일반적인 pipe()로 생성하는 anonymous IPC pipe와는 다르다.

Linux tracing subsystem이 제공하는 특수한 interface이며, tracing buffer의 내용을 user space에서 stream 형태로 읽을 수 있게 한다.

8. eBPF Program Compile​

eBPF 프로그램은 일반 C 프로그램처럼 실행파일로 compile하지 않는다.

다음과 같이 BPF target으로 compile 한다.

clang -g -O2 -target bpf \
    -D__TARGET_ARCH_x86 \
    -I. \
    -c memwatch.bpf.c \
    -o memwatch.bpf.o
clang: C 코드를 컴파일한다.
-g: 디버깅 정보 생성. BTF/CO-RE를 사용하는 eBPF에서도 필요한 정보를 생성
-O2: 최적화 레벨 2. eBPF에서는 verifier가 처리하기 좋은 코드 생성 등을 위해 보통 최적화를 켜서 컴파일
-target bpf: x86 기계어가 아니라 eBPF bytecode를 생성. 가장 핵심적인 옵션
-D__TARGET_ARCH_x86: __TARGET_ARCH_x86 매크로를 정의한다. libbpf가 대상 CPU architecture가 x86임을 알도록 하기 위함.
-I.: header를 찾을 때 현재 디렉터리(.)도 검색. 여기서는 #include "vmlinux.h" 등을 찾을 수 있음
-c memwatch.bpf.c: memwatch.bpf.c를 링크하지 않고 object file까지만 컴파일
-o memwatch.bpf.o: 결과 파일 이름을 memwatch.bpf.o로 지정

디렉터리는 다음과 같은 상태가 되었다.

memwatch.bpf.c
memwatch.bpf.o
victim.c
victim.out
vmlinux.h

이 파일은 Kernel에 load할 eBPF object file이다.

9. BPF Object​

일반 프로그램과 eBPF 프로그램의 차이는 다음과 같다.

일반 C 프로그램

victim.c
   ↓
gcc
   ↓
victim.out
   ↓
CPU에서 실행

반면 eBPF 프로그램은:

memwatch.bpf.c
      ↓
clang -target bpf
      ↓
memwatch.bpf.o
      ↓
Kernel에 load
      ↓
Kernel hook에 attach
      ↓
Event 발생
      ↓
eBPF program 실행

10. User-space Loader​

일반적으로 BPF application에는 BPF object를 kernel에 올리는 user-space loader가 존재한다.

하지만 현재 프로젝트에서는 아직 이 user-space 프로그램을 만들지 않았다.

따라서 누가 kernel에 load할 수가 없다.

이번에는 별도의 loader를 작성하지 않고 이미 존재하는 user-space tool인 bpftool을 loader 대신 사용했다.

즉:

현재

사용자
   ↓
bpftool
   ↓
Kernel BPF subsystem

구조다.

11. BPF Program Load​

다음 명령으로 BPF object를 kernel에 load했다.

sudo bpftool prog load memwatch.bpf.o /sys/fs/bpf/memwatch
memwatch.bpf.o
      ↓
Kernel로 전달
      ↓
BPF verifier
      ↓
Kernel BPF program 생성

구조다.

12. Kernel Load​

다음 명령으로 kernel에 존재하는 BPF program을 확인했다.

sudo bpftool prog show

그 결과 다음 program을 확인했다.

따라서:

memwatch.bpf.o
      ↓
Kernel
      ↓
trace_mmap

까지 성공했다.

13. Kernel Attach​

BPF program이 kernel에 load되었다고 해서 event에 연결된 것은 아니다.

개념적으로 이 두 단계는 구분된다.

LOAD

BPF object
   ↓
Kernel BPF program


ATTACH

Kernel BPF program
   ↓
특정 kernel hook

현재 program은:

SEC("tracepoint/syscalls/sys_enter_mmap")

이므로 최종적으로 다음 hook에 연결되어야 한다.

syscalls:sys_enter_mmap

14. autoattach​

다음과 같이 attach했다.

sudo bpftool prog load \
    memwatch.bpf.o \
    /sys/fs/bpf/memwatch \
    autoattach

BPF source에 이미:

SEC("tracepoint/syscalls/sys_enter_mmap")

가 있기 때문에 libbpf/bpftool이 section 정보를 이용해 해당 program을 tracepoint에 attach한다.

개념적으로:

memwatch.bpf.o
      ↓
LOAD
      ↓
Kernel BPF program
      ↓
SEC("tracepoint/syscalls/sys_enter_mmap")
      ↓
AUTO ATTACH
      ↓
syscalls:sys_enter_mmap
