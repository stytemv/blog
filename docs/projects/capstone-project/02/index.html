캡스톤 프로젝트 #2 — User-space Loader / Ring Buffer 구현

개요​

이전 글에서는 victim 프로그램이 mmap()을 호출했을 때 sys_enter_mmap tracepoint에 연결한 eBPF 프로그램이 실행되는지 확인했다. 당시에는 BPF object의 load와 attach를 bpftool로 직접 수행하고, bpf_printk()의 출력은 trace_pipe에서 읽었다.

이 구조로 커널에서 eBPF 프로그램이 실행된다는 사실은 확인할 수 있었지만, 실제 분석 프로그램의 형태는 아니었다. BPF 프로그램을 사용하려면 매번 수동으로 load와 attach를 수행해야 했고, 출력도 PID=...처럼 문자열에 의존했다. 또한 모든 프로세스의 mmap() 호출이 함께 출력되므로 특정 프로세스만 관찰하기 어려웠다.

두번째 목표로는 기존의 sys_enter_mmap tracepoint를 유지하면서 사용자 공간 프로그램인 memwatch.c를 작성하고, 커널과 사용자 공간 사이의 이벤트 전달 경로를 추가했다.

                         User Space
────────────────────────────────────────────────────
memwatch.c
   │
   ├── BPF object load / attach (Skeleton)
   ├── 감시할 PID 설정 (BPF map)
   ├── Ring Buffer polling
   └── 대상 프로그램 실행 (선택)
                   │
───────────────────┼────────────────────────────────
                   │     Kernel Space
                   ▼
            sys_enter_mmap
                   ↓
             trace_mmap()
                   ↓
          target PID 확인
                   ↓
         struct mem_event 작성
                   ↓
              Ring Buffer
                   │
───────────────────┼────────────────────────────────
                   ▼
                memwatch
                   ↓
             handle_event()
                   ↓
               로그 출력

현재 구현한 tracepoint는 여전히 sys_enter_mmap 하나다. 또한 mmap()의 인자나 반환 주소를 기록하는 기능도 아직 추가되지 않았다. 이번 글에서는 eBPF 프로그램을 로드하고 실행할 수 있는 User-space 프로그램을 구현하고, 명령행 인자를 통해 감시 대상 프로세스를 지정하는 기능을 추가한다.

1. User-space Loader 작성​

1.1 bpftool에서 사용자 공간 프로그램으로​

이전에는 다음 명령으로 BPF object를 커널에 적재했다.

sudo bpftool prog load memwatch.bpf.o /sys/fs/bpf/memwatch autoattach

memwatch.bpf.o는 일반적인 실행 파일이 아니라 BPF 명령어 및 섹션 정보가 들어 있는 ELF object다. 그렇기 때문에 이 파일을 생성했다고 해서 코드가 바로 실행되지는 않는다. 커널에 적재하는 load 과정과 특정 이벤트에 연결하는 attach 과정이 필요하다.

memwatch.bpf.c
     ↓ clang -target bpf
memwatch.bpf.o
     ↓ load
Kernel BPF program
     ↓ attach
syscalls:sys_enter_mmap
     ↓ 이벤트 발생
trace_mmap()

bpftool도 사용자 공간에서 이러한 작업을 수행하는 프로그램이다. 다만 이전 단계에서는 별도의 User-space Loader를 직접 구현하지 않고, bpftool을 이용해 eBPF 프로그램을 커널에 로드하고 sys_enter_mmap tracepoint에 attach했다.

이번 단계에서는 이러한 로드 및 attach 과정을 직접 작성한 User-space 프로그램에서 수행하도록 변경했다.

이를 위해 libbpf를 이용해 load와 attach를 memwatch.c에서 수행하도록 변경했다.

libbpf는 사용자 공간에서 BPF object, map, program, link 등을 관리하기 위한 라이브러리다.

저수준 API로 각각을 관리하는 대신, 이번 구현에서는 BPF Skeleton을 사용했다.

1.2 Skeleton 생성​

먼저 기존과 같이 BPF 프로그램을 컴파일한다.

clang -O2 -g -target bpf -D__TARGET_ARCH_x86 -I. \
    -c memwatch.bpf.c -o memwatch.bpf.o

이후 bpftool을 이용하여 Skeleton Header를 생성한다.

bpftool gen skeleton memwatch.bpf.o > memwatch.skel.h

Skeleton은 BPF Object File을 기반으로 bpftool이 자동 생성하는 C Header이다. BPF 프로그램과 Map 등의 정보를 포함하며, User-space 프로그램에서 이를 관리하기 위한 libbpf 기반 인터페이스를 제공한다.

이전 단계에서는 bpftool을 이용하여 BPF 프로그램을 Load 및 Attach했지만, 이번에는 직접 작성한 User-space 프로그램에서 해당 작업을 수행한다.

Skeleton을 사용하면 BPF Object를 관리하는 코드를 직접 작성하는 대신, 자동 생성된 구조체와 함수를 이용하여 BPF 프로그램의 Load, Attach 및 자원 관리를 수행할 수 있다.

생성된 memwatch.skel.h에서는 다음과 같은 함수들을 제공한다.

  • memwatch_bpf__open() : 사용자 공간에서 BPF object와 관련 관리 구조를 준비한다. 이 시점에는 커널에 프로그램이 적재되지 않았다.
  • memwatch_bpf__load() : BPF map을 생성하고, 필요한 relocation을 처리한 뒤 verifier 검사를 거쳐 프로그램을 커널에 적재한다.
  • memwatch_bpf__attach() : BPF 소스의 SEC("tracepoint/syscalls/sys_enter_mmap") 정보를 이용해 실제 tracepoint에 연결한다.
  • memwatch_bpf__destroy() : Skeleton이 소유하는 BPF link, 파일 디스크립터와 사용자 공간 리소스를 정리한다.

memwatch.skel.h는 직접 작성하는 파일이 아니라 BPF Object에서 자동 생성되는 파일이다.

따라서 memwatch.bpf.c를 수정했다면 BPF Object를 다시 컴파일하고 Skeleton도 재생성해야 한다.

사용자 공간에서는 아래처럼 생성된 함수를 호출할 수 있다.

struct memwatch_bpf *skel = memwatch_bpf__open();
if (!skel) {
    fprintf(stderr, "Failed to open BPF skeleton\n");
    return 1;
}

int err = memwatch_bpf__load(skel);
if (err)
    goto cleanup;

err = memwatch_bpf__attach(skel);
if (err)
    goto cleanup;

/* 이후 이벤트 처리 */

cleanup:
    memwatch_bpf__destroy(skel);

BPF 프로그램을 메모리에 준비하는 것과 커널에 적재하는 것, 특정 이벤트에 연결하는 것은 별개의 과정이다.

기존의 bpf_printk()를 유지한 상태에서도 사용자 공간 로더가 BPF 프로그램을 적재하고 이벤트에 연결하는지 검증할 수 있다.

다만 이렇게만 작성하면 사용자 공간의 memwatch가 이벤트 데이터를 직접 수신하지는 않는다. 다음으로 문자열 기반 출력 대신 이벤트 전달 경로를 구현했다.

2. Ring Buffer를 이용한 이벤트 전달​

이전 코드에서는 다음 함수로 PID, TID, COMM을 출력했다.

bpf_printk("PID=%u TID=%u COMM=%s", pid, tid, comm);

bpf_printk()는 초기 실행 여부를 확인하는 데 적합하지만, 이벤트를 수집하고 처리하기 위한 주된 인터페이스로 사용하기에는 한계가 있다.

출력이 문자열이므로 사용자 공간에서 항목을 다시 해석해야 하고, 이후 mprotect나 munmap처럼 이벤트 종류가 늘어나면 출력 형식도 각각 관리해야 한다.

Ring Buffer는 데이터를 순환형 버퍼에 저장하고, 저장된 순서대로 읽어 처리하는 자료구조이다. 버퍼의 끝에 도달하면 다시 처음 위치부터 공간을 재사용한다.

eBPF에서는 Kernel에서 발생한 이벤트를 User-space 프로그램으로 전달하는 데 사용한다. BPF 프로그램이 Ring Buffer에 이벤트를 기록하면, User-space 프로그램이 이를 읽어 처리할 수 있게 한다.

따라서 BPF 프로그램에서 공통 구조체를 생성하고, 이를 Ring Buffer를 통해 사용자 공간으로 전달하도록 변경했다.

                    Kernel
sys_enter_mmap
     ↓
trace_mmap()
     ↓
struct mem_event
     ↓ bpf_ringbuf_submit()
BPF Ring Buffer
     │
─────┼────────────────────────
     │             User Space
     ▼
ring_buffer__poll()
     ↓
handle_event()
...

2.2 공통 이벤트 구조체 — memwatch.h​

커널 BPF 프로그램과 사용자 공간 프로그램은 서로 별도로 컴파일된다.

따라서 Kernel에서 기록한 이벤트 데이터를 User-space에서도 동일한 필드 구성과 크기로 해석할 수 있도록 공통 구조체를 정의해야 한다.

따라서 memwatch.h를 다음과 같이 작성했다.

#ifndef MEMWATCH_H
#define MEMWATCH_H

/*
 * Event Type
 * 발생한 메모리 관련 이벤트의 종류를 구분
 * 추후 mprotect, munmap 등 추가 예정
 */
enum mem_event_type {
    MEM_EVENT_MMAP = 1,
};

/*
 * Memory Event
 * eBPF에서 생성하여 Ring Buffer를 통해
 * User-space로 전달할 공통 데이터 구조체
 * __u32, __u64는 포함 전에 정의되어 있어야 함
 */
struct mem_event {
    __u64 timestamp_ns; // 커널 단조 시계, ns
    __u32 pid;          // TGID
    __u32 tid;          // TID
    __u32 type;         // enum mem_event_type
    __u32 reserved;     // 정렬을 위한 예약 영역
    char comm[16];      // TASK_COMM_LEN
};

#endif

현재 이벤트 종류는 MEM_EVENT_MMAP 하나뿐이다. 그러나 type을 별도 필드로 두면 이후 mprotect, munmap 등 새로운 이벤트가 추가되어도 수신 측에서 이벤트를 구분할 수 있다.

timestamp_ns는 bpf_ktime_get_ns()에서 얻은 나노초 값이다. 커널의 단조 시간(monotonic time)에 기반한 값이지 날짜와 시각을 나타내는 벽시계 시간은 아니다.

pid는 프로세스 단위 식별을 위한 TGID이고, tid는 해당 이벤트를 발생시킨 스레드의 ID다. comm[16]은 현재 태스크의 이름을 보관하며, 전체 실행 경로를 의미하지 않는다.

reserved는 현재 사용하는 데이터 배치에서 정렬과 향후 확장을 고려한 필드다. 현재 소스에서는 vmlinux.h 또는 <linux/types.h>를 통해 __u32, __u64를 정의한 뒤 이 헤더를 포함한다.

2.3 BPF Ring Buffer map 선언​

memwatch.bpf.c에 다음 map을 추가했다.

struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);
} events SEC(".maps");

BPF_MAP_TYPE_RINGBUF는 BPF Ring Buffer를 생성하는 map 유형이다.

max_entries는 Ring Buffer가 사용할 데이터 영역의 크기로, 여기서는 256 KiB로 지정했다. SEC(".maps")는 이 선언이 BPF object의 map 관련 섹션에 들어가도록 한다.

이벤트 발생 시에는 Ring Buffer에서 레코드를 위한 공간을 확보한다.

struct mem_event *e = bpf_ringbuf_reserve(
    &events, sizeof(struct mem_event), 0);
if (!e)
    return 0;

bpf_ringbuf_reserve()는 지정한 크기의 레코드를 저장할 공간을 예약하고 그 공간을 가리키는 포인터를 반환한다.

공간을 확보하지 못하면 NULL을 반환하므로, 현재 구현은 해당 이벤트를 건너뛴다.

예약에 성공하면 구조체를 채운다.

e->timestamp_ns = bpf_ktime_get_ns();
e->pid = pid;
e->tid = tid;
e->type = MEM_EVENT_MMAP;
e->reserved = 0;
bpf_get_current_comm(e->comm, sizeof(e->comm));

bpf_ringbuf_submit(e, 0);

bpf_ringbuf_submit()을 호출하면 작성한 레코드가 소비자에게 전달 가능한 상태가 된다. 이 시점의 BPF 프로그램은 문자열을 출력하지 않고 구조체 데이터를 발행한다.

2.4 User-space의 Ring Buffer 처리​

사용자 공간에서는 Ring Buffer map에 접근하기 위해 해당 map의 파일 디스크립터가 필요하다. Skeleton이 제공하는 skel->maps.events를 이용해 다음과 같이 소비자를 생성한다.

rb = ring_buffer__new(
    bpf_map__fd(skel->maps.events),
    handle_event,
    NULL,
    NULL);

bpf_map__fd()는 BPF 프로그램에서 정의하고 Kernel에 생성한 Ring Buffer Map의 파일 디스크립터(FD)를 가져온다.

이후 ring_buffer__new()를 이용하여 해당 Ring Buffer의 이벤트를 수신할 객체를 생성하고, 이벤트를 처리할 콜백 함수인 handle_event()를 등록한다.

handle_event()는 memwatch.c에 작성된 일반적인 User-space 함수이다. BPF 프로그램이 Ring Buffer에 이벤트를 기록하면, User-space 프로그램은 ring_buffer__poll()을 통해 이벤트를 수신하고 handle_event()에서 해당 데이터를 처리한다.

static int handle_event(void *ctx, void *data, size_t data_sz)
{
    (void)ctx;
    const struct mem_event *e = data;

    if (data_sz < sizeof(*e))
        return 0;

    if (e->type == MEM_EVENT_MMAP) {
        printf("[MMAP] TIME=%llu PID=%u TID=%u COMM=%s\n",
               (unsigned long long)e->timestamp_ns,
               e->pid, e->tid, e->comm);
    }
    return 0;
}

콜백 인자 data는 수신된 이벤트 레코드의 시작 주소다. data_sz가 구조체보다 작으면 해당 데이터를 해석하지 않고 반환하도록 했다. 이벤트 종류가 MEM_EVENT_MMAP인 경우에만 해당 정보를 출력한다.

이후 다음 루프로 수신을 진행한다.

while (!exiting) {
    int ret = ring_buffer__poll(rb, 100);
    if (ret == -EINTR)
        continue;
    if (ret < 0)
        break;
}

ring_buffer__poll()은 Ring Buffer에 기록된 이벤트를 확인하고, 이벤트가 있다면 앞서 등록한 콜백 함수인 handle_event()를 호출하여 데이터를 처리한다.

ring_buffer__poll(rb, 100)에서 100은 대기 시간을 밀리초(ms) 단위로 지정한 값이다. 처리할 이벤트가 없다면 최대 100ms 동안 새로운 이벤트를 기다리고, 이벤트가 발생하면 이를 처리한다. 지정한 시간이 지나도 이벤트가 없다면 대기를 종료하고 반환한다.

반환값이 -EINTR인 경우에는 대기 도중 Signal에 의해 작업이 중단되었다는 의미이다. 따라서 이를 일반적인 오류와 구분하여 처리했다.

이후 최종 코드에서는 이벤트를 수신하는 동안 실행한 자식 프로세스의 종료 여부도 주기적으로 확인할 수 있도록 해당 루프를 확장했다.

이 과정까지 구현하면 eBPF 프로그램의 출력이 더 이상 trace_pipe에 의존하지 않는다.

3. 특정 PID만 감시하도록 변경​

3.1 모든 mmap 이벤트를 출력하는 문제​

감시 대상 PID 필터링​

현재 BPF 프로그램은 sys_enter_mmap Tracepoint에 Attach되어 있으므로, 감시 대상과 관계없이 시스템에서 발생하는 mmap() 호출에 반응한다.

따라서 사용자가 지정한 프로세스의 이벤트만 수집하려면, 현재 mmap()을 호출한 프로세스의 PID와 사용자가 입력한 PID를 비교해야 한다.

이를 위해 BPF_MAP_TYPE_ARRAY를 사용했다.

struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, __u32);
} target_pid_map SEC(".maps");

BPF_MAP_TYPE_ARRAY는 일반적인 배열과 유사하게 Key를 인덱스로 사용하여 Value를 저장하고 조회하는 BPF Map이다.

여기서 target_pid_map은 정의한 BPF Map의 이름이며, max_entries를 1로 설정했으므로 Key 0에 하나의 값만 저장할 수 있다.

User-space 프로그램인 memwatch.c에서는 사용자가 지정한 PID를 bpf_map_update_elem()을 통해 해당 Map의 Key 0에 저장한다.

예를 들어 사용자가 PID 1234를 지정했다면 Map에는 다음과 같이 저장된다.

target_pid_map
+-----+-------+
| Key | Value |
+-----+-------+
|  0  | 1234  |
+-----+-------+

이렇게 저장된 PID는 Kernel에서 실행되는 BPF 프로그램에서도 조회할 수 있다.

다음은 현재 이벤트를 발생시킨 프로세스의 PID를 구하고, Map에 저장된 감시 대상 PID와 비교하는 코드이다.

__u64 id = bpf_get_current_pid_tgid();
__u32 pid = id >> 32;
__u32 tid = (__u32)id;

__u32 key = 0;
__u32 *target_pid = bpf_map_lookup_elem(&target_pid_map, &key);

if (!target_pid || *target_pid == 0 || pid != *target_pid)
    return 0;

먼저 bpf_get_current_pid_tgid()는 현재 BPF 프로그램을 실행하게 만든 프로세스 및 스레드의 식별 정보를 64비트 값으로 반환한다.

상위 32비트에는 TGID가, 하위 32비트에는 TID가 저장된다.

63                       32 31                        0
+--------------------------+---------------------------+
|           TGID           |            TID            |
+--------------------------+---------------------------+

TGID는 일반적인 User-space 프로그램에서 getpid()로 얻는 프로세스 ID에 해당하며, TID는 현재 실행 중인 스레드의 ID이다. 같은 프로세스에 속한 스레드들은 TGID를 공유하지만 TID는 서로 다를 수 있다.

따라서 감시 대상 프로세스의 모든 스레드에서 발생하는 mmap() 호출을 확인하기 위해 상위 32비트인 TGID를 pid에 저장한다.

이후 다음 코드를 통해 앞서 정의한 target_pid_map에서 감시 대상 PID를 조회한다.

__u32 key = 0;
__u32 *target_pid = bpf_map_lookup_elem(&target_pid_map, &key);

bpf_map_lookup_elem()은 지정한 BPF Map에서 Key에 해당하는 Value를 조회하는 함수이다.

여기서는 target_pid_map의 Key 0에 저장된 값을 조회하며, 반환된 포인터를 target_pid에 저장한다. 따라서 *target_pid로 해당 PID 값을 참조할 수 있다.

마지막으로 다음 조건문을 통해 현재 프로세스가 감시 대상인지 확인한다.

if (!target_pid || *target_pid == 0 || pid != *target_pid)
    return 0;

각 조건은 다음을 의미한다.

  • !target_pid: Map 조회에 실패하여 유효한 포인터를 얻지 못한 경우
  • *target_pid == 0: 감시 대상 PID가 설정되지 않은 경우
  • pid != *target_pid: 현재 이벤트를 발생시킨 프로세스의 PID가 감시 대상 PID와 다른 경우

위 조건 중 하나라도 만족하면 BPF 프로그램은 return 0으로 종료하여 해당 이벤트를 무시한다.

반대로 현재 프로세스의 PID와 감시 대상 PID가 일치하면 이후 코드가 실행되어 이벤트 정보를 Ring Buffer에 기록한다.

이처럼 BPF_MAP_TYPE_ARRAY를 통해 User-space에서 지정한 PID를 BPF 프로그램에 전달하고, Kernel에서 PID를 비교하도록 구현했다. 이를 통해 감시 대상이 아닌 프로세스의 이벤트는 Ring Buffer에 기록하지 않도록 필터링할 수 있다.

3.3 사용자 공간에서 PID 설정​

사용자 공간에서는 먼저 명령행 인자를 PID로 해석한다. 단순히 atoi()를 사용하지 않고 strtol()을 이용해 변환 오류와 범위를 확인하도록 했다.

errno = 0;
parsed_pid = strtol(argv[1], &endptr, 10);

if (errno != 0 || endptr == argv[1] || *endptr != '\0' ||
    parsed_pid <= 0 || parsed_pid > INT_MAX) {
    fprintf(stderr, "Invalid PID: %s\n", argv[1]);
    return 1;
}

위 코드는 PID 전용 모드를 설명하기 위한 검증 코드다. 최종 구현에서는 프로그램 경로도 받을 수 있도록 pid_mode를 별도로 판별한다.

BPF 프로그램을 load한 뒤 사용자 공간에서 map 값을 설정한다.

__u32 key = 0;
__u32 target_pid = (__u32)parsed_pid;

if (bpf_map_update_elem(
        bpf_map__fd(skel->maps.target_pid_map),
        &key, &target_pid, BPF_ANY) != 0) {
    perror("bpf_map_update_elem");
}
memwatch 3418
    ↓
bpf_map_update_elem()
    ↓
target_pid_map[0] = 3418
    │
────┼──────────────────────────────────
    │ Kernel
    ▼
sys_enter_mmap
    ↓
현재 TGID == 3418 ?
    ├── Yes → Ring Buffer로 이벤트 전달
    └── No  → return 0

실제 PID 지정 모드에서는 다음 형태의 출력을 확인했다.

memwatch started. Target PID: 3418
Press Ctrl-C to exit.
[MMAP] TIME=706526989350 PID=3418 TID=3418 COMM=victim

이제 특정 프로세스의 mmap 이벤트를 따로 볼 수 있게 되었지만, 여전히 실행 직후 이벤트를 관찰하기 어려운 문제가 남아 있었다.

4. 대상 프로그램 자동 실행​

4.1 기존 PID 방식의 한계​

PID 지정 모드에서는 감시 대상 프로세스의 PID를 알아야 하므로, 먼저 victim 프로그램을 실행한 후 해당 PID를 확인해야 한다.

터미널 A: ./victim
             ↓
         PID 확인
             ↓
터미널 B: sudo ./memwatch <PID>
             ↓
         감시 시작

이 방식은 victim을 실행한 이후에 memwatch를 실행하므로, BPF 프로그램이 Attach되기 전에 발생한 mmap() 이벤트는 수집할 수 없다는 한계가 있다.

이를 해결하기 위해 memwatch가 직접 대상 프로그램을 시작하는 모드를 추가했다.

sudo ./memwatch 3418       # 이미 실행 중인 PID 감시
sudo ./memwatch ./victim   # 준비 후 victim 실행

단순히 fork() 후 곧바로 execvp()를 호출하면 여전히 문제가 생길 수 있다.

자식이 먼저 실행되어 mmap()을 호출하고, 부모가 그 뒤에 BPF 프로그램을 attach할 수 있기 때문이다. 따라서 부모의 감시 준비가 끝날 때까지 자식을 대기 시키도록 해야한다.

4.2 pipe(), fork(), execvp() 사용​

부모와 자식이 순서를 맞추기 위해 익명 pipe를 사용했다.

memwatch (부모)                         child
       │                                  │
       ├────────── pipe() ────────────────┤
       ├────────── fork() ────────────────┤
       │                              read() 대기
       │                                  │
       ├── target_pid_map에 PID 설정     │
       ├── BPF attach                     │
       ├── Ring Buffer consumer 생성      │
       │                                  │
       ├────────── write('S') ──────────> │
       │                              execvp()
       │                                  │
       └────── Ring Buffer polling <──────┘

이번 구현에서 pipe의 목적은 데이터 전송 자체가 아니라 동기화다. 자식은 read()로 한 바이트를 기다리고, 부모는 PID map 설정·BPF attach·Ring Buffer 생성까지 끝낸 후 'S' 한 바이트를 기록한다.

4.3 자식 프로세스 대기​

자식 프로세스의 핵심 코드는 다음과 같다.

if (child_pid == 0) {
    char start_signal;
    ssize_t n;
    close(pipefd[1]);

    signal(SIGINT, SIG_DFL);
    signal(SIGTERM, SIG_DFL);
    signal(SIGPIPE, SIG_DFL);

    do {
        n = read(pipefd[0], &start_signal, 1);
    } while (n < 0 && errno == EINTR);
    close(pipefd[0]);

    if (n != 1 || start_signal != 'S')
        _exit(1);

    execvp(argv[1], &argv[1]);
    perror("execvp");
    _exit(127);
}

자식은 부모로부터 신호를 받기 전까지 대상 프로그램을 실행하지 않는다. execvp(argv[1], &argv[1])는 ./victim뿐 아니라 명령행에서 전달한 나머지 인자도 함께 전달한다.

부모는 fork()로 얻은 자식 PID를 그대로 감시 대상 PID로 사용한다.

target_pid = (__u32)child_pid;

이후 bpf_map_update_elem()로 PID를 map에 기록하고, memwatch_bpf__attach() 및 ring_buffer__new()를 수행한다. 모든 준비가 완료되면 pipe에 'S'를 기록한다.

char start_signal = 'S';
ssize_t n;
do {
    n = write(pipefd[1], &start_signal, 1);
} while (n < 0 && errno == EINTR);

if (n != 1) {
    perror("Failed to release child");
    goto cleanup;
}
close(pipefd[1]);
pipefd[1] = -1;

자식은 execvp() 이후에도 같은 PID를 유지하므로 앞서 설정한 PID 필터가 그대로 적용된다.

다만 자식의 시작을 동기화한다고 해도 Ring Buffer 공간 부족 등으로 인한 이벤트 손실 가능성이 없어지는 것은 아니다.

4.4 자식 종료 확인과 자원 정리​

memwatch는 이벤트를 수신하는 동안 자식 프로세스가 종료되었는지도 확인해야 한다. 이를 위해 waitpid()와 WNOHANG 옵션을 사용했다.

pid_t result = waitpid(child_pid, &child_status, WNOHANG);
if (result == child_pid) {
    child_reaped = 1;
    /* 남은 Ring Buffer 이벤트를 한 차례 처리한 후 종료 */
    break;
}

WNOHANG을 지정하면 자식이 아직 실행 중일 때 waitpid()가 종료를 기다리며 블로킹하지 않는다. 따라서 이벤트 polling 루프를 유지하면서 종료 여부를 주기적으로 확인할 수 있다.

SIGINT나 SIGTERM을 받으면 signal handler가 exiting 플래그를 설정하고, 루프에서 빠져나온다. 마지막에는 Ring Buffer를 해제하고 Skeleton을 파괴한다. launcher 모드에서 자식이 아직 살아 있다면 SIGTERM을 보내고 waitpid()로 회수하도록 했다.

이때 BPF link 역시 Skeleton의 수명에 종속된다. memwatch가 종료되고 link가 정리되면 기존 tracepoint 연결이 유지된다고 가정할 수 없다. 다시 관찰하려면 로더를 다시 실행해 load와 attach를 수행해야 한다.

또 하나의 제약이 있다. sudo ./memwatch ./victim으로 실행하면 자식은 별도의 권한 변경을 수행하지 않는 한 root 권한을 상속한다.

5.2 memwatch.bpf.c​

#include "vmlinux.h"
#include "memwatch.h"
#include <bpf/bpf_helpers.h>

char LICENSE[] SEC("license") = "GPL";

/* Ring Buffer: Kernel → User-space 이벤트 전달 */
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);
} events SEC(".maps");

/* 사용자 공간에서 감시할 PID를 지정하는 ARRAY map */
struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, __u32);
} target_pid_map SEC(".maps");

SEC("tracepoint/syscalls/sys_enter_mmap")
int trace_mmap(struct trace_event_raw_sys_enter *ctx)
{
    __u64 id = bpf_get_current_pid_tgid();
    __u32 pid = id >> 32;
    __u32 tid = (__u32)id;

    /* PID filtering: 감시 대상만 이벤트 발행 */
    __u32 key = 0;
    __u32 *target_pid = bpf_map_lookup_elem(&target_pid_map, &key);
    if (!target_pid || *target_pid == 0 || pid != *target_pid)
        return 0;

    /* Ring Buffer에 공통 구조체 공간 예약 */
    struct mem_event *e = bpf_ringbuf_reserve(
        &events, sizeof(struct mem_event), 0);
    if (!e)
        return 0;

    e->timestamp_ns = bpf_ktime_get_ns();
    e->pid = pid;
    e->tid = tid;
    e->type = MEM_EVENT_MMAP;
    e->reserved = 0;
    bpf_get_current_comm(e->comm, sizeof(e->comm));

    bpf_ringbuf_submit(e, 0);
    return 0;
}

5.3 memwatch.c​

#include <stdio.h>
#include <stdlib.h>             // strtol()
#include <limits.h>             // INT_MAX
#include <errno.h>              // errno, EINTR
#include <signal.h>             // signal(), kill()
#include <unistd.h>             // pipe(), fork(), read(), write(), execvp()
#include <sys/types.h>          // pid_t
#include <sys/wait.h>           // waitpid()
#include <linux/types.h>        // __u32, __u64
#include <bpf/bpf.h>            // bpf_map_update_elem()
#include <bpf/libbpf.h>         // Ring Buffer API

#include "memwatch.h"
#include "memwatch.skel.h"

static volatile sig_atomic_t exiting = 0;

/* SIGINT(Ctrl-C), SIGTERM 발생 시 종료 표시 */
static void sig_handler(int sig)
{
    (void)sig;
    exiting = 1;
}

/* Ring Buffer에서 수신된 공통 이벤트를 출력 */
static int handle_event(void *ctx, void *data, size_t data_sz)
{
    (void)ctx;
    const struct mem_event *e = data;
    if (data_sz < sizeof(*e))
        return 0;

    if (e->type == MEM_EVENT_MMAP) {
        printf("[MMAP] TIME=%llu PID=%u TID=%u COMM=%s\n",
               (unsigned long long)e->timestamp_ns,
               e->pid, e->tid, e->comm);
    }
    return 0;
}

int main(int argc, char **argv)
{
    struct memwatch_bpf *skel = NULL;
    struct ring_buffer *rb = NULL;
    __u32 target_pid = 0;
    __u32 key = 0;

    pid_t child_pid = -1;
    int pipefd[2] = {-1, -1};
    int child_status = 0;
    int child_reaped = 0;

    char *endptr;
    long parsed_pid;
    int pid_mode;
    int err = 0;

    /* 숫자는 PID, 그 외는 프로그램 경로 */
    if (argc < 2) {
        fprintf(stderr, "Usage: %s <PID | PROGRAM> [ARGS...]\n", argv[0]);
        return 1;
    }

    errno = 0;
    parsed_pid = strtol(argv[1], &endptr, 10);
    pid_mode = (endptr != argv[1] && *endptr == '\0');

    if (pid_mode) {
        if (argc != 2 || errno != 0 ||
            parsed_pid <= 0 || parsed_pid > INT_MAX) {
            fprintf(stderr, "Invalid PID or arguments\n");
            return 1;
        }
        target_pid = (__u32)parsed_pid;
    } else if (argv[1][0] == '-') {
        fprintf(stderr, "Invalid program path: %s\n", argv[1]);
        return 1;
    }

    signal(SIGINT, sig_handler);
    signal(SIGTERM, sig_handler);
    signal(SIGPIPE, SIG_IGN);

    /* Step 1: Open */
    skel = memwatch_bpf__open();
    if (!skel) {
        fprintf(stderr, "Failed to open BPF skeleton\n");
        return 1;
    }

    /* Step 2: Load */
    err = memwatch_bpf__load(skel);
    if (err) {
        fprintf(stderr, "Failed to load BPF skeleton: %d\n", err);
        goto cleanup;
    }

    /* Launcher 모드에서 부모-자식 동기화 파이프 준비 */
    if (!pid_mode) {
        if (pipe(pipefd) == -1) {
            perror("pipe");
            err = -1;
            goto cleanup;
        }

        child_pid = fork();
        if (child_pid < 0) {
            perror("fork");
            err = -1;
            goto cleanup;
        }

        if (child_pid == 0) {
            char start_signal;
            ssize_t n;
            close(pipefd[1]);

            /* 부모 signal handler를 자식이 상속하지 않도록 복원 */
            signal(SIGINT, SIG_DFL);
            signal(SIGTERM, SIG_DFL);
            signal(SIGPIPE, SIG_DFL);

            do {
                n = read(pipefd[0], &start_signal, 1);
            } while (n < 0 && errno == EINTR);
            close(pipefd[0]);

            if (n != 1 || start_signal != 'S')
                _exit(1);

            /* PID 유지한 채 자식 이미지를 victim 등으로 교체 */
            execvp(argv[1], &argv[1]);
            perror("execvp");
            _exit(127);
        }

        /* 부모는 fork()가 반환한 자식 PID를 감시 대상으로 사용 */
        close(pipefd[0]);
        pipefd[0] = -1;
        target_pid = (__u32)child_pid;
    }

    /* BPF ARRAY map의 key=0에 PID 기록 */
    err = bpf_map_update_elem(
        bpf_map__fd(skel->maps.target_pid_map),
        &key, &target_pid, BPF_ANY);
    if (err) {
        perror("Failed to update target PID map");
        goto cleanup;
    }

    /* Step 3: Attach */
    err = memwatch_bpf__attach(skel);
    if (err) {
        fprintf(stderr, "Failed to attach BPF skeleton: %d\n", err);
        goto cleanup;
    }

    /* Ring Buffer consumer + callback 등록 */
    rb = ring_buffer__new(
        bpf_map__fd(skel->maps.events), handle_event, NULL, NULL);
    if (!rb) {
        fprintf(stderr, "Failed to create Ring Buffer\n");
        err = -1;
        goto cleanup;
    }

    printf("memwatch started. Target PID: %u\n", target_pid);
    printf("Press Ctrl-C to exit.\n");
    fflush(stdout);

    /* 준비 완료 후 자식의 execvp() 허용 */
    if (!pid_mode) {
        char start_signal = 'S';
        ssize_t n;
        if (exiting) {
            err = -EINTR;
            goto cleanup;
        }
        do {
            n = write(pipefd[1], &start_signal, 1);
        } while (n < 0 && errno == EINTR);
        if (n != 1) {
            perror("Failed to release child");
            err = -1;
            goto cleanup;
        }
        close(pipefd[1]);
        pipefd[1] = -1;
    }

    /* 이벤트 수집 및 launcher의 자식 종료 확인 */
    while (!exiting) {
        err = ring_buffer__poll(rb, 100);
        if (err == -EINTR) {
            err = 0;
            continue;
        }
        if (err < 0) {
            fprintf(stderr, "Ring Buffer polling failed: %d\n", err);
            break;
        }

        if (!pid_mode) {
            pid_t result = waitpid(child_pid, &child_status, WNOHANG);
            if (result == child_pid) {
                child_reaped = 1;
                int remaining = ring_buffer__poll(rb, 0);
                if (remaining < 0 && remaining != -EINTR)
                    err = remaining;
                else
                    err = 0;
                printf("Target process %d exited.\n", child_pid);
                break;
            }
            if (result < 0 && errno != EINTR) {
                perror("waitpid");
                err = -1;
                break;
            }
        }
    }

cleanup:
    /* Step 4: Destroy */
    if (pipefd[0] >= 0)
        close(pipefd[0]);
    if (pipefd[1] >= 0)
        close(pipefd[1]);

    /* 미종료 자식을 종료시키고 회수 */
    if (child_pid > 0 && !child_reaped) {
        kill(child_pid, SIGTERM);
        while (waitpid(child_pid, &child_status, 0) < 0 &&
               errno == EINTR) {
        }
    }

    ring_buffer__free(rb);
    memwatch_bpf__destroy(skel);
    return err < 0 ? 1 : 0;
}

memwatch.bpf.c는 감시 PID에 해당하는 mmap 진입 이벤트만 struct mem_event로 발행한다. memwatch.c는 PID 또는 프로그램 경로를 받아 BPF 프로그램을 로드하고, 대상 PID를 설정하고, 이벤트를 수신한다.

6. Build 및 실행​

새로운 환경에서는 clang, llvm, gcc, bpftool, libbpf 개발 헤더, libelf 개발 헤더 및 pkg-config 호환 도구가 필요하다. Ubuntu 환경에서는 다음과 같이 설치할 수 있다.

sudo apt update
sudo apt install -y clang llvm gcc make bpftool libbpf-dev libelf-dev pkgconf

먼저 현재 실행 중인 커널의 BTF 정보를 C header로 변환한다.

bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h

/sys/kernel/btf/vmlinux는 C header 파일이 아니라 BTF metadata다. BPF 프로그램이 참조할 커널 타입 정보를 vmlinux.h 형태로 생성한다. 다른 커널이나 노트북으로 개발 환경을 옮긴 경우에도 현재 환경의 BTF를 기준으로 다시 생성하는 편이 안전하다.

BPF object를 컴파일한 다음 Skeleton을 생성한다.

clang -O2 -g -target bpf -D__TARGET_ARCH_x86 -I. \
    -c memwatch.bpf.c -o memwatch.bpf.o

bpftool gen skeleton memwatch.bpf.o > memwatch.skel.h

주요 컴파일 옵션은 이전 글과 동일하다. -target bpf는 BPF 명령어를 생성하도록 지정한다.

-O2는 최적화, -g는 디버그 및 BTF 관련 정보 생성을 위해 사용했고, -I.는 현재 디렉터리의 vmlinux.h, memwatch.h 등을 찾기 위한 설정이다.

-D__TARGET_ARCH_x86은 BPF 관련 아키텍처 매크로를 정의한다. 실제 빌드 환경의 아키텍처에 맞게 설정해야 한다.

사용자 공간 로더와 테스트 프로그램은 일반적인 실행 파일로 컴파일한다.

gcc -O2 -g memwatch.c -o memwatch $(pkg-config --cflags --libs libbpf)
gcc -O2 -g victim.c -o victim

여기서 $(...)는 shell의 명령 치환(command substitution)이다. pkg-config --cflags --libs libbpf의 출력이 컴파일과 링크에 필요한 옵션으로 전달된다. 이 명령이 실패한다면 pkgconf 또는 libbpf 개발 패키지의 설치 상태를 확인해야 한다.

컴파일 순서는 다음과 같다.

vmlinux.h ─────────────────────┐
memwatch.h ────────────────────┤
                               ▼
memwatch.bpf.c ──clang──> memwatch.bpf.o
                                  │
                                  ▼
                         bpftool gen skeleton
                                  │
                                  ▼
                           memwatch.skel.h
                                  │
memwatch.c ───────────────────────┤
                                  ▼
                             gcc + libbpf
                                  │
                                  ▼
                               memwatch

BPF 소스가 변경되면 .bpf.o와 .skel.h도 다시 생성해야 한다. 반대로 사용자 공간 코드인 memwatch.c만 수정했다면 보통 사용자 공간 실행 파일만 다시 컴파일하면 된다.

실행은 두 가지 방법을 지원한다.

# 실행 중인 프로세스의 PID를 지정
sudo ./memwatch 3418

# memwatch가 대상 프로그램을 직접 실행
sudo ./memwatch ./victim

memwatch는 자식으로 실행한 victim의 PID 3551을 자동으로 감시 대상으로 지정했다. victim이 자신의 PID를 출력하기 전부터 동일한 PID의 mmap 진입 이벤트가 Ring Buffer를 통해 전달되는 것을 확인할 수 있다. 자식이 종료된 뒤에는 종료 메시지가 출력되었다.

시작 부분에 여러 [MMAP] 로그가 나타나는 것은 프로그램 시작 과정에서도 메모리 매핑이 발생하기 때문이다. 다만 현재 이벤트에는 주소·길이·보호 플래그·파일 디스크립터가 포함되지 않으므로, 각 줄이 어떤 목적의 매핑인지 확정할 수 없다.

또한 아래 출력은 구분해서 해석해야 한다.

[MMAP] TIME=... PID=3551 TID=3551 COMM=victim
[2] mprotect()
[3] munmap()

[MMAP]은 eBPF가 전달한 sys_enter_mmap 이벤트다. 반면 [2] mprotect()와 [3] munmap()은 victim 프로그램의 printf() 출력이다.

이번 결과는 BPF 프로그램의 load 및 attach, 특정 PID의 이벤트 필터링, Ring Buffer를 통한 데이터 수신, 프로그램 실행 전 감시 준비와 종료 처리까지 작동했음을 보여준다.

8. 현재 구현 범위와 다음 단계​

현재 구현한 기능은 다음과 같다.

  • sys_enter_mmap tracepoint에 eBPF 프로그램 연결
  • PID(TGID), TID, COMM 및 단조 시간 수집
  • BPF 프로그램과 사용자 공간의 공통 이벤트 구조체 정의
  • Ring Buffer를 통한 정형 이벤트 전달
  • BPF ARRAY map을 이용한 PID 필터링
  • PID 지정 모드 및 프로그램 자동 실행 모드
  • 자식 실행 전 attach 준비, 자식 종료 감지 및 리소스 정리

반면 아직 mmap()의 요청 주소·길이·보호 플래그·매핑 플래그·파일 디스크립터는 수집하지 않는다. 시스템 콜 진입 시점인 sys_enter_mmap만 사용하므로 반환값이나 실제 매핑 주소도 확인할 수 없다. 이를 위해서는 이후 sys_exit_mmap과 연관된 데이터를 다루는 기능이 필요하다.
